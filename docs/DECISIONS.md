### 2026-08-30 — localStorage Quota Crash Fix

* **What:** Chat send was dead ("nothing happened") because `chat.store.ts` zustand `persist` `setItem` threw `QuotaExceededError` on every `addMessage` (and `removeContext`), aborting `handleSend` before `executeRealAnalysis`. Root cause: persistence stored full messages including large image `preview` data URLs and unbounded history, exceeding the ~5MB `localStorage` budget. Fixes: (a) `chat.store.ts` now uses a **quota-safe storage wrapper** (try/catch with one-shot prune-to-last-30 retry) so store updates never throw; (b) `partialize` strips `preview`/`file` from contexts and caps history at 50; (c) `useSessionPersistence.ts` uses `prepareForStorage()` to strip previews, cap at 50, and never persist huge blobs. Existing oversized `satiq-chat-v1` is self-healed on first trimmed write.
* **Why:** Browser `localStorage` is shared 5MB; data-URL image previews (base64, multi-MB each) and full streamed answers blow it fast, and the default zustand `setItem` surfaces the quota error up into the dispatch path.
* **Consequences:** `frontend npm run build` passes (2574→ unchanged module count). Sends no longer crash; persistence becomes best-effort. Trade-off: restored sessions no longer show image previews (stripped to save quota) — conversation text/charts retained. KeyError risk removed.

### 2026-08-30 — False "Generation failed" + Pipeline Latency Fix

* **What:** User reported (1) the UI showed "Generation failed / The last request was interrupted. Retry" while the pipeline was **still running** in the background, and (2) the LLM planner/router steps each took ~94–97s. Two root causes fixed: (a) **Gateway poll budget too short** — `agentic-analysis.provider.ts` polled `ORCH /api/v1/task` for only `maxAttempts=120 × 300ms = 36s` then yielded `error: orchestrator_timeout`, which the frontend renders as the failed/interrupted banner (see `ChatCanvas.tsx:91`). Bumped to `maxAttempts=720 × 500ms = 360s` (configurable via `ORCH_POLL_MAX_ATTEMPTS` / `ORCH_POLL_MS`). (b) **Slow LLM routing** — the planner used the heavy `GROQ_MODEL` (qwen 27B) at `max_tokens=800`; planner + router are sequential so ~190s combined. Now planner and router both use the fast `GROQ_ROUTER_MODEL` (`groq/compound-mini`), planner `max_tokens` 800→300, composer `max_tokens` 600→400, and Groq clients set `max_retries=1` to kill SDK backoff delays (latency > 8s now fails fast to the existing mock fallback instead of retrying for 30s+).
* **Why:** The orchestrator pipeline genuinely runs 90s+ on a real (throttled) Groq model; giving up at 36s only produced a false failure while the backend kept working. Planner/router are routing/intent steps that do not need a 27B model.
* **Consequences:** `gateway tsc` OK, `frontend build` OK, `orchestrator` imports OK. Live test: `call_qwen_router` 1.51s, `call_qwen_planner` 1.42s (was ~94s/97s) — ~64× faster. The composer still uses `GROQ_MODEL` (real qwen) and is the only remaining Groq-bound step; it streams tokens live so the UI no longer shows a false failure, and the 360s budget guarantees completion. To make the composer itself faster, set `GROQ_MODEL` to a faster Groq model (e.g. the router model) — left as a user choice to preserve answer quality.

### 2026-08-30 — Real Thinking Text + Perpetual-Timer Fix

* **What:** User reported (1) the thinking phase text was not shown in the chat, and (2) the response "never stopped" — timers kept incrementing even after Stop, with no clear bounded terminal state. Root causes: (a) live `answer_delta` tokens are emitted by `response_composer_node` **during** `pipeline.ainvoke`, but `composer_started` (which creates the chat message + sets `lastAssistantId`) was emitted *after* ainvoke, so `applyEvent` dropped every live token and then `streamed=True` skipped re-emitting — the answer never reached the chat and `thinkingStreaming` stayed stuck. (b) The only `thinking_delta` was a static string; real planner/router reasoning was never surfaced. (c) On `cancelled`/`error`, `applyEvent` set `globalStatus` but did not flip the message's `streaming`/`thinkingStreaming` flags, so `StreamingResponseCard`'s clock interval ran forever; `RightThinkingPanel` ran its clock interval unconditionally; and pipeline steps that never got a completion event stayed "running" with no frozen `durationMs`, so their timers ticked indefinitely. Fixes: planner/router nodes made `async` and now `emit("thinking_delta", …)` with their real reasoning (router classification + planner reasoning) during the run; `composer_started` emitted **before** `pipeline.ainvoke` so live answer deltas are captured; `applyEvent` now flips `streaming`/`thinkingStreaming`/`thinkingCollapsed` false on `cancelled` and `error`; `execution.store.setGlobalStatus` now freezes any still-running/pending step's `durationMs` on terminal; `RightThinkingPanel` clock interval stops when `globalStatus` is terminal; `StreamingResponseCard` clock interval stops when neither thinking nor answer is streaming; gateway poll budget default tightened 360s→240s to bound stuck/dropped runs.
* **Why:** A dropped/finished-but-unconfirmed stream (or a dev gateway HMR restart) left frontend state "running" forever; the chat needs the model's actual reasoning visible, not a fake placeholder.
* **Consequences:** `frontend npm run build` + `gateway npx tsc --noEmit` pass; orchestrator graph still compiles with async planner/router nodes (verified). Now thinking shows real text (e.g. "🔀 Router: classified as `grounding`… / 🧭 Planner (groq): …") and streams before the answer; timers freeze the moment a run completes, is stopped, or errors — no more perpetual increment. Trade-off: if the gateway is restarted mid-run in dev (HMR), the in-flight execution is lost and must be retried — production (docker) does not auto-restart.

### 2026-08-30 — Composer Think-Tag Stripping + Edit/Retry UX

* **What:** Root cause of "answer stops after three words / pipeline never reaches the end": the Groq `qwen/qwen3.6-27b` composer emits `<think>…</think>` chain-of-thought as part of its stream. The composer (`call_qwen_composer_stream` / `call_qwen_composer` in `orchestrator/core/llm_client.py`) did NOT strip it (only the router did), so with `max_tokens=400` the reasoning tokens consumed the budget and the real answer was squeezed to a few words; the frontend also hides raw `<think>` text, so the user saw "three words and stops". Fix: (1) added async streaming `_strip_think_tokens` generator that buffers and drops `<think>…</think>` (handles tags split across chunks); (2) wrapped both composer paths in it; (3) added an explicit "do NOT use `<think>` tags / no internal reasoning" instruction to the composer prompt; (4) raised composer `max_tokens` 400→700 so the answer gets the budget. Net effect: real Groq composer now returns a clean ~229-char answer in ~2.2s (was 90s+ generating reasoning). Also added UX: user messages now have an **Edit** ActionChip that prefills the Composer (`chat.store.composerPrefill`), and the existing **Regenerate**/Retry on assistant messages re-runs the last prompt.
* **Why:** The model thinking is not the answer; surfacing it as the answer both wastes token budget and confuses the user. Disabling/stripping thinking also removed the latency the user reported.
* **Consequences:** `frontend npm run build` + `gateway npx tsc --noEmit` pass; `orchestrator/tests/test_pipeline.py` 4 passed; direct `run_pipeline` E2E confirms `answer_delta` chunks carry the real answer (chart + bbox) with no `<think>` and reaches `query_completed`. Files: `orchestrator/core/llm_client.py`, `frontend/src/store/chat.store.ts`, `frontend/src/components/chat/Composer.tsx`, `frontend/src/components/chat/MessageItem.tsx`. The 4 vision-model families stay mocked; only LLM text is real.
